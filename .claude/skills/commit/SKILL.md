# commit: 변경사항 분석 후 컨벤션 커밋

현재 저장소의 변경사항을 분석해 **논리적 단위별로** 커밋 계획을 세우고 커밋한다.

## 실행 모드

| 모드 | 활성 조건 | 동작 |
|------|-----------|------|
| **승인 모드** (기본) | 아래 조건에 해당하지 않을 때 | 커밋 계획을 보여주고 승인 후 커밋 |
| **자동 모드** | 인자에 `--auto`가 있거나, 요청에 "바로 커밋", "승인 없이", "묻지 말고", "알아서 커밋" 등이 포함될 때 | 계획 수립 후 승인 없이 즉시 커밋하고 결과만 보고 |

모드는 1~3단계에는 영향이 없고 4단계 동작만 바꾼다. 자동 모드에서도 "커밋하면 안 되는 파일" 제외 규칙과 금지 사항은 그대로 지킨다.

## 1. 변경사항 분석

다음 명령으로 현재 상태를 파악한다 (병렬 실행 가능).

```bash
git status --short
git diff              # unstaged 변경
git diff --staged     # staged 변경
git log --oneline -10 # 기존 커밋 스타일 참고
```

- untracked 파일은 `git status`에서 확인하고, 필요하면 내용을 직접 읽어 성격을 파악한다.
- 이미 staged된 변경이 있으면 사용자가 의도적으로 묶은 것일 수 있으므로 그 범위를 우선 존중한다.
- 변경사항이 없으면 "커밋할 변경사항이 없습니다"라고 알리고 종료한다.

### 커밋하면 안 되는 파일

아래에 해당하면 커밋 대상에서 제외하고 사용자에게 알린다.

- 비밀 정보: `.env`, `*.pem`, `*.key`, credentials/토큰이 포함된 파일
- 빌드 산출물·의존성: `dist/`, `build/`, `node_modules/` 등 (`.gitignore` 누락 의심 시 함께 안내)
- 디버그용 임시 코드(`console.log` 남발, 주석 처리된 대량 코드 등)는 커밋 전 사용자에게 확인

## 2. 논리적 단위로 분류

변경사항을 **하나의 목적 = 하나의 커밋** 원칙으로 묶는다.

- 기능 추가와 버그 수정, 리팩터링, 설정 변경은 서로 다른 커밋으로 분리한다.
- 같은 기능을 위해 함께 바뀐 파일(컴포넌트 + 타입 + 테스트 등)은 하나로 묶는다.
- 한 파일 안에 성격이 다른 변경이 섞여 있으면 승인 모드에서는 사용자에게 분리 여부를 묻는다 (interactive `git add -p`는 사용할 수 없으므로, 분리가 필요하면 방법을 제안한다). 자동 모드에서는 묻지 않고 그 파일의 주된 변경 목적에 맞는 커밋에 포함한다.
- 변경이 작고 단일 목적이면 굳이 쪼개지 않는다.

## 3. 커밋 메시지 작성

### 형식

```
<type>: <한국어 요약>

<본문 (선택)>
```

### type

| type | 용도 |
|------|------|
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변화 없는 코드 구조 개선 |
| `chore` | 빌드·설정·의존성·문서 등 기타 작업 |

### 규칙

- 요약은 **한국어**, 50자 이내, 마침표 없이, "~추가", "~수정", "~개선"처럼 명사형으로 끝낸다.
  - 예: `feat: 컴포넌트 미리보기 패널 추가`
  - 예: `fix: 빈 프롬프트 입력 시 서버 오류 수정`
  - 예: `refactor: API 호출 로직을 커스텀 훅으로 분리`
  - 예: `chore: ESLint 설정 및 의존성 업데이트`
- **무엇을**보다 **왜**가 중요하면 본문에 1~3줄로 이유를 적는다. 사소한 변경이면 본문은 생략한다.
- 시스템/프로젝트에서 지정한 attribution 라인(예: `Co-Authored-By:`)이 있으면 메시지 끝에 붙인다.

## 4. 커밋 실행

### 승인 모드 (기본)

커밋 전에 반드시 아래 형식으로 계획을 보여주고 승인을 받는다.

```
커밋 계획 (총 N개)

[1] feat: 컴포넌트 미리보기 패널 추가
    - src/components/Preview.tsx
    - src/types/preview.ts

[2] chore: ESLint 설정 업데이트
    - eslint.config.js

제외: .env (비밀 정보 포함 가능)
```

- 사용자가 승인하면 커밋 단위별로 순서대로 실행한다.
  ```bash
  git add <해당 파일들>
  git commit -m "<메시지>"
  ```
  여러 줄 메시지는 heredoc(Bash) 또는 here-string(PowerShell)을 사용한다.
- `git add -A` / `git add .`는 제외 대상 파일이 섞일 수 있으므로 사용하지 않고, 파일을 명시한다.
- 사용자가 메시지나 분류 수정을 요청하면 반영한 계획을 다시 보여주고 재승인을 받는다.
- 커밋 후 `git log --oneline -N`으로 결과를 보여준다.

### 자동 모드

- 계획을 세운 즉시 승인 없이 커밋 단위별로 순서대로 커밋한다 (`git add <파일들>` → `git commit`, 파일은 명시).
- 완료 후 아래 형식으로 결과만 보고한다.
  ```
  커밋 완료 (총 N개)
  a1b2c3d feat: 컴포넌트 미리보기 패널 추가
  e4f5g6h chore: ESLint 설정 업데이트

  제외: .env (비밀 정보 포함 가능)
  ```
- 결과가 마음에 들지 않으면 사용자가 되돌릴 수 있도록 `git reset --soft HEAD~N`으로 취소할 수 있다고 한 줄 안내한다 (직접 실행하지는 않는다).
- 자동 모드라도 아래 경우에는 **커밋을 멈추고 사용자에게 확인**한다.
  - 비밀 정보로 의심되는 내용이 커밋 대상 파일 안(diff)에서 발견된 경우
  - merge/rebase 충돌 상태이거나 충돌 마커(`<<<<<<<`)가 남아 있는 경우
  - pre-commit hook이 실패했고 원인 수정이 단순하지 않은 경우

## 금지 사항

- 승인 모드에서는 사용자 승인 없이 커밋하지 않는다.
- `git push`, `--amend`, `--no-verify`, `reset --hard` 등은 사용자가 명시적으로 요청하지 않는 한 사용하지 않는다.
- pre-commit hook이 실패하면 우회하지 말고 원인을 보고·수정한 뒤 **새 커밋**으로 다시 시도한다.
- 기본 브랜치(main/master)에서 커밋하려는 경우, 계획을 보여줄 때 현재 브랜치를 함께 알린다.
