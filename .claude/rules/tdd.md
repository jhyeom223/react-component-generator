# TDD Rule

> **경고: 이 규칙은 Rigid — 상황에 맞게 변형하지 마라.**
> 예외는 아래 "적용 기준"에 명시된 것뿐이다. 그 밖의 해석·완화·생략은 허용하지 않는다.

## 0. 우선순위

- 프로젝트의 `CLAUDE.md` / `AGENTS.md`(하위 디렉토리 포함)에 TDD 규칙이 있으면 **그 규칙이 우선한다.**
- 이 파일은 **기본값(fallback)** 이다. 프로젝트 규칙이 다루지 않는 부분에만 적용한다.
- 테스트 실행 명령은 프로젝트 문서에 정의된 것을 사용한다.

## 1. 적용 기준

### TDD 필수

- **비즈니스 로직** (도메인 규칙, 상태 전이, 계산)
- **API** (라우트 핸들러, 요청 검증, 응답·에러 매핑)
- **유틸리티 / 순수 함수** (파서, 변환기, 포맷터)
- **버그 수정** — 버그를 재현하는 실패 테스트를 **먼저** 작성한다
- 사용자 상호작용에 따라 동작이 달라지는 컴포넌트 로직 (활성/비활성, 입력 처리, 콜백 호출)

### TDD 불필요

- **타입 정의** (`type`, `interface`만 있는 파일)
- **설정 파일** (빌드, 린트, tsconfig, 환경 설정)
- **순수 UI** (동작 없이 마크업·스타일만 바꾸는 변경)
- **SQL** (스키마, 마이그레이션, 쿼리 정의)
- 문서, 주석, 정적 에셋

판단이 애매하면 **필수 쪽으로 분류한다.**

## 2. RED-GREEN-REFACTOR 사이클

### RED — 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 한 테스트에서 여러 동작을 검증하지 않는다.
- 테스트 이름은 검증하는 동작을 문장으로 서술한다.
- **반드시 실행해서 실패를 확인한다.** 실행하지 않은 RED는 RED가 아니다.
- 실패 이유가 **"기능 미구현"** 이어야 한다. 문법 오류, import 경로 오류, 오타로 인한 실패는 RED가 아니다 — 고친 뒤 다시 실행한다.
- 작성 직후 통과한다면 테스트가 잘못되었거나 이미 구현된 동작이다. 테스트를 재검토한다.

### GREEN — 최소 구현

- 방금 실패한 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI:** 아직 테스트가 요구하지 않는 분기, 옵션, 추상화를 추가하지 않는다.
- **신규 테스트 + 기존 테스트 전체를 실행해 모두 통과를 확인한다.**
- 기존 테스트가 깨지면 GREEN이 아니다. 테스트를 수정해 맞추지 말고 구현을 고친다 (요구사항 변경이 명확한 경우만 예외).

### REFACTOR — 구조 개선

- **중복 제거, 이름 개선, 헬퍼 추출**만 한다.
- 단계마다 테스트를 실행해 **green을 유지한다.**
- **새 동작 추가 금지.** 새 동작이 필요하면 RED로 돌아간다.
- 테스트 코드도 리팩터링 대상이다.

### 반복

- 다음 동작을 하나 골라 **RED로 돌아간다.**
- 요구사항의 모든 동작이 테스트로 덮일 때까지 사이클을 반복한다.

## 3. 삭제 강제 규칙

- 테스트보다 **프로덕션 코드를 먼저 작성했다면 삭제하고 RED부터 재시작한다.**
- **"참고용"으로 남기는 것도 금지한다.** 주석 처리, 별도 파일 보관, 다른 브랜치 보관 모두 포함한다.
- 삭제한 코드를 기억에서 그대로 옮겨 쓰지 않는다. 테스트가 요구하는 만큼만 다시 작성한다.

## 4. 변명 차단표

| 변명 | 반론 |
|------|------|
| "너무 단순해서 테스트 불필요" | 단순하면 테스트도 1분이면 끝난다. 단순한 코드일수록 나중에 조건이 붙으며 깨진다. |
| "나중에 추가하겠다" | 나중은 오지 않는다. 구현 후 작성한 테스트는 구현을 따라 쓰게 되어 버그를 잡지 못한다. |
| "시간이 없다" | 디버깅과 회귀 수정이 테스트 작성보다 오래 걸린다. TDD가 가장 빠른 경로다. |
| "삭제하면 낭비" | 매몰 비용이다. 테스트 없이 남은 코드는 검증되지 않은 부채이며, 다시 쓰는 비용이 더 작다. |
| "프로토타입이다" | 프로토타입은 그대로 프로덕션이 된다. 버릴 코드라면 이 저장소에 커밋하지 않는다. |

## 5. 완료 조건

- 모든 동작에 대응하는 테스트가 있고, **전체 테스트가 통과한다.**
- 각 테스트는 작성 시점에 한 번 실패한 이력이 있다 (RED 확인).
- 위 조건을 충족하지 못하면 작업을 완료로 보고하지 않는다.
